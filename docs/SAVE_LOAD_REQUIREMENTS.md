# セーブ＆ロード 要件定義案

作成日：2026-09-26。対象：`proto/index.html` のブラウザ版。
状態：手動セーブなしの方針を採用（2026-09-26）。実装と検証状況は末尾を参照。

## 1. 目的と基本方針

ブラウザを閉じたり再読み込みしたりしても、育成・装備・探索の進行を引き継いで遊べるようにする。

初期リリースは **1プロフィール・オートセーブ・中断再開** を推奨する。ロードは最新の保存済み状態からの再開とし、過去の任意時点を選んでやり直す機能は設けない。探索中断を帰還扱いにせず、戦利品の確定、死亡時のロスト、仲間の扱いは既存仕様に従う。

ユーザーの指定により、手動セーブ・複数スロットは実装しない。

## 2. 現状と実装上の接点

- `proto/index.html` は進行をメモリに保持しており、同ファイル内に永続保存処理はない。
- `S` にアカウント進行、主人公、探索記録がある。`P` にプレイヤーの位置・戦闘状態、`W` に現在階の地形・敵・ドロップなどがある。`S` だけの保存では探索を復元できない。
- `startRun()` は探索回数・持ち込み品などを更新するため、ロード時には実行しない。`enterFloor()` も敵・宝箱を再生成するので、そのままロード経路に使わない。
- 現在のタイトルの「冒険を続ける」はメモリ内の主人公を判定して街へ進む導線であり、保存データをロードする機能ではない。
- `die()`、`finishReturn()`、死亡後の再出発、ボス報酬、仲間の蘇生・見捨てなどは保存と整合させる必要がある。
- 未追跡の `alpha.js` などを保存機能の正本として扱わない。演出ファイルとの接続は `VISUAL_DEVELOPMENT.md` を参照する。

## 3. 初期リリースの範囲

| 項目 | 要件 |
|---|---|
| 保存場所 | 同一ブラウザ・同一配信元の端末内に保存。ログイン不要 |
| プロフィール数 | 1つ。内部復旧用の直前の正常データは別に保持 |
| 通常操作 | 自動保存のみ。通常操作用の保存ボタンは設けない |
| 再開 | タイトルの「つづきから」で街または探索の保存地点を復元 |
| 中断中 | ゲーム時間を進めない。回復・クールダウン・状態異常・敵の行動を進めない |
| 対象外 | クラウド同期、端末間共有、複数スロット、任意時点への巻き戻し、初版でのファイル入出力 |

ファイル直開きは現行の起動方法なので、正式にサポートするかは実装前に確定する。推奨は固定URLで配信するブラウザ版を保証対象にすること。ファイル直開きを対象外にする場合はREADMEと起動案内も更新する。保存先の変更・ブラウザデータ削除を越えた復元は保証しない。

## 4. 保存データ

保存対象は専用の定義で管理し、実行中のオブジェクトを丸ごと無条件で保存しない。以下の分類は初期棚卸しであり、実装時は `S / P / W` に加えて、それ以外の変数・コールバックに保持された進行も確認する。

| 分類 | 保存する内容 |
|---|---|
| 識別・記録 | 名前、世代に関係する死亡回数、探索回数、到達最深、生還最深、クリア記録、初回案内の既読 |
| 財産・育成 | 所持金、SP、鉱石、倉庫・伝説倉庫、所有履歴、施設、能力強化、武器熟練度、武器技と命名、大技と強化、遺物と装備 |
| 主人公・仲間 | レベル、経験値、能力、現在HP、装備の固有性能・耐久・鑑定状態、恩寵、編成、酒場待機者・候補、慰霊碑 |
| 解放・抽選結果 | 中継地点、開始階、一度きりの報酬フラグ、ボス撃破状態、店の品揃え、持ち込み、ガチャ残数と更新日、呪いと更新週、生成の塩 |
| 探索 | 階層、未確定の戦利品・金・鉱石、経過時間、撃破数、護符、回復・蘇生などの使用済み状態、仲間の喪失記録 |
| 現在階 | 地形、探索済みマス、敵の生死・HP・位置・AI状態、床アイテム・宝箱、墓、NPC、イベント、鉱脈・採掘、試練、ハザード |
| 戦闘の継続 | 味方位置、敵味方の状態異常、行動待ち時間、予兆、弾、持続攻撃、多段攻撃の残り、追従に必要な状態、戦闘・報酬用乱数の状態 |
| 未完了の選択 | 恩寵選択、倉庫あふれ、仲間の蘇生判断、死亡後の継承などの種別・候補・確定済み状態 |
| 設定 | 地図表示など、再起動後も引き継ぐと定義した設定 |

画像、Canvas、DOM、関数、入力の押下状態、純粋な装飾粒子・画面揺れ・ダメージ文字は保存しない。演出用に見える変数でも、当たり判定・報酬確定・進行停止に関与する部分は保存対象と分離する。デバッグ設定は従来どおり保存しない。デバッグによる進行変更を通常セーブへ混入させない検証モードを設ける。

日次・週次の更新は既存の暦ルールに従い、ロード回数によって抽選回数や商品が増えないようにする。端末時計の改変対策は初版の対象外。

## 5. 保存タイミングと一貫性

| タイミング | 要件 |
|---|---|
| 新規開始 | 名前・初期主人公の作成が完了した状態を保存 |
| 街での変更 | 購入・売却・鑑定・修理・強化・倉庫移動・装備・編成・抽選などの確定後に保存 |
| 出発・階層移動 | 持ち込み消費と新しい階の生成が完了した一貫した状態を保存 |
| 探索中 | 変更があれば5秒間隔を初期値として保存。値は実機計測で調整 |
| 重要な確定 | 死亡、帰還、ボス報酬、宝箱・墓の回収、一度きりの報酬、仲間の喪失・蘇生を一括して保存 |
| 選択画面 | 候補提示時の保留状態と、選択確定後の状態をそれぞれ保存。ロードで候補を引き直さない |
| ブラウザを閉じる・再読み込み | 終了前の追加保存を試みる。終了時の処理が走らなくても直近の自動保存を利用 |
| 背景へ移動 | 一時停止し、追加保存を試みる。終了時イベントだけには依存しない |

- 主人公・アカウント・探索・現在階は同一リビジョンのスナップショットとして扱い、一部だけ新しい状態にしない。
- 書き込みを直列化し、古い保存処理が新しい保存結果を上書きしない。
- 保存時点はゲーム処理の途中ではなく、更新または操作の完了境界に置く。
- 消費と獲得、ロストと墓生成、帰還報酬と探索終了は不可分の更新にする。重要処理の確定を利用者へ表示する前に保存成功を確認する。
- 重要保存の失敗時は進行を停止し、メモリ内の確定結果を保持して再試行できる。報酬処理そのものを再実行しない。
- 異常終了時は最後に正常保存できた状態へ戻る。通常探索の目標損失は5秒程度であり、OSによる強制終了や保存障害時まで厳密な上限を保証するものではない。
- ローカルデータの意図的な書き換え・バックアップ差し戻しを完全に防ぐことは対象外。正常なロードによる重複獲得や復活は防止する。

## 6. ロードと画面の挙動

1. 起動時に保存データを検査し、有効な場合は「つづきから」を表示する。名前、保存日時、街／第何階層かを添える。
2. ロードは検証・必要な形式移行・参照復元を完了してからゲームへ反映する。失敗時は現在のデータを変更しない。
3. 街なら街へ、探索中なら同じ階・同じ位置・同じ状況へ戻す。探索回数の加算、HP回復、敵や宝箱の再配置は行わない。
4. 探索再開時は一時停止した画面に「再開」を表示し、操作するまで戦闘を進めない。入力をクリアし、時間計測の基準を再設定する。
5. 未完了の選択は同じ候補で再表示する。死亡確定後は死亡結果または既存ルールに沿った次の進行へ戻し、死ぬ前の探索へ戻さない。
6. 広告視聴中に終了した場合、完了が記録されていない報酬は付与しない。完了済みの報酬は二重に付与しない。広告サービスとの検証方法は別途設計する。

保存表示は「保存中」「保存しました」「保存できません」を区別する。保存中表示だけで成功扱いにしない。通常の成功は小さく通知し、失敗は再試行と最終保存日時を表示する。

「はじめから」は既存データがあるときだけ上書き確認を行う。削除対象を明記し、新規状態の保存が成功するまで既存データを維持する。設定の全消去と既存デバッグの全消去は永続データ・復旧データも対象とし、再読み込みで復活しないようにする。

## 7. 破損・更新・競合への対応

- 保存データに形式バージョン、ゲーム版、プロフィールID、リビジョン、保存日時、進行フェーズを持たせる。
- ロード時は型、数値の範囲、ID参照、配列サイズ、必須項目を検査する。名前や技名をHTMLとして実行しない。
- 旧形式は対応範囲を決めて移行する。移行成功まで元データを残す。未知の新形式や復元不能なデータを勝手に初期化しない。
- 主データが壊れている場合は直前の正常データからの復旧を案内し、その保存日時と失われる可能性のある進行を示す。正常な死亡のやり直し用には公開しない。
- 保存不可・容量不足でも起動不能にしない。保存できないことを明示し、一時プレイを選んだ場合は終了後に残らない旨を表示する。
- 複数タブの同時書き込みを防ぎ、後から開いたタブはプレイ開始を止めるか閲覧状態にする。制御権の移動時には最新データを読み直す。
- 保存処理の例外でゲームループを壊さない。復旧不能でもユーザー操作なしに全消去しない。

## 8. 実装方針案と性能条件

保存用モジュールを分離し、本体に保存・復元の接点を設ける。初版はlocalStorageの1キーに進行全体を書き込み、アカウントと探索の部分更新を避ける。同期書き込みにより操作完了境界で保存失敗を検知する。直前の正常データは別キーに保持する。複数タブはWeb Locksで書き込み権を排他制御する。最大データ量・実機で性能目標を満たさない場合はIndexedDBへの移行を検討する。

オブジェクト参照はスナップショット内のIDで保存し、仲間・装備・効果の所有者を復元する。TypedArrayや乱数生成器の内部状態は明示的に変換する。地形は初版では生成済みデータの保存を優先し、生成アルゴリズム変更で同じ種から違う階ができる問題を避ける。

初期性能目標：代表端末で通常保存を1秒以内、ロードを2秒以内に完了させる。小規模階と敵・弾・戦利品の多い階の両方で計測し、保存に起因する50ms超のメインスレッド停止を生じさせないことを目指す。未達時は周期だけを延ばして隠さず、形式・データ量・処理分割を見直す。対象端末と最大データ量は実装着手時に確定する。

## 9. 受け入れ条件

| ID | シナリオと合格条件 |
|---|---|
| SL-01 | 初回プレイ→街で装備・購入・強化→再読み込みで、名前・財産・装備・育成が一致 |
| SL-02 | 探索中に敵を倒して拾得→中断→再開で、位置・HP・敵・地形・戦利品・探索済みマスが一致 |
| SL-03 | 弾・予兆・多段攻撃・状態異常・クールダウン中に再開しても、ダメージが消失／二重発生せず、待ち時間が初期化されない |
| SL-04 | 出発・階層移動をまたぐロードで、探索回数・持ち込み品・敵・宝箱が増減しない |
| SL-05 | 主人公の死亡確定直後に再読み込みしても、既存のロスト・墓・継承・次代への進行が一度だけ成立 |
| SL-06 | 帰還・ボス撃破・一度きりの報酬の直前／保存中／保存直後の中断で、消費と獲得が分離せず、報酬を二重取得できない |
| SL-07 | 仲間の死亡判断・恩寵選択・倉庫あふれの途中から、同じ候補で操作を完了できる |
| SL-08 | アプリを背景へ移して戻した場合と再起動した場合の両方で、不在時間ぶんの戦闘進行がなく、明示操作まで停止 |
| SL-09 | 保存不可・容量不足・破損・未知バージョンでも黙って初期化せず、適切な復旧／再試行案内が出る |
| SL-10 | 形式移行で装備固有値・所有関係・進行フラグを維持。失敗しても元データが残る |
| SL-11 | 複数タブと遅延した保存処理で、新しい進行を古い状態が上書きしない |
| SL-12 | 新規開始・全消去後に旧データが復活しない。デバッグ設定・検証用進行が通常データに混入しない |
| SL-13 | 対象Safari／Chromeでブラウザ終了→再起動後に再開でき、規定の性能を満たす |

テストは専用の保存領域を使い、実プレイデータに触れない。保存経路の追加に伴う既存の戦闘・街・死亡・帰還・演出の回帰確認も行う。

## 10. 実装前の決定事項と順序

| 決定事項 | 推奨案 |
|---|---|
| ロードの用途 | 中断再開。過去へ自由に戻るスロット方式は採用しない |
| 初版の完成範囲 | 街の進行保存と探索途中の復元の両方。街だけの段階は内部検証用とする |
| 配信・保証対象 | 固定URLのブラウザ版。ファイル直開きの扱いは別途明示 |
| バックアップ持ち出し | JSONの書き出し・取り込みは次段階。公開運用で必要なら初版に繰り上げる |

実装順序は、保存対象の完全な棚卸し → 保存形式と失敗時処理 → 街の保存 → 探索と戦闘の復元 → 死亡・報酬・選択途中の一貫性 → UI・形式移行・実機試験とする。

ゲームバランスの数値は変更しない。中断再開が戦闘やロストへ与える影響を上記の条件で検証し、既存仕様と矛盾が出た場合は保存の都合で戦闘ルールを変えず、設計上の判断事項として扱う。


## 11. 実装の対応状況（2026-09-26）

- `proto/save-load.js`：保存形式、参照・Set・Map・TypedArrayの復元、チェックサム、直前データ、排他制御、失敗時停止、タイトル／再開表示。
- `proto/index.html`：乱数生成器の状態取得、操作・フレーム完了境界、保存データからのタイトル再開、恩寵候補の再表示。
- `proto/game-feel.js`：ボス演出中に保留している遷移先をデータとして公開。報酬・ダメージ・AIの式は変更しない。
- 純粋な描画演出は再生成。ボス撃破演出の途中は報酬が確定した選択画面へ戻す。通常の街メニュー・鞄・説明画面は街または探索へ戻し、恩寵・帰還選択・仲間死亡・消耗品の使用先・未受け取りのガチャ結果・最終ボスの結果画面は復元する。
- デバッグの利用後は再読み込みまで通常セーブを更新しない。検証専用URL `?save=off` は永続データを読み書きしない。
- 保存領域や排他制御を利用できない環境では開始を止めて案内する。「保存なしで一時プレイを選ぶ」UIは初版では未提供。
- 初版の形式はversion 1。過去の永続形式はないため移行処理はまだ不要。未対応バージョンを検出した場合は、古いバックアップへの自動差し戻しや初期化を行わない。
- 既知の関数はゲーム定義の登録キーからのみ復元し、文字列からコードを評価しない。定義テーブルの構成変更時には保存形式の互換性判断と必要な移行を追加する。
- Safari／iPhone実機、ストレージの長期保持、配信元を変更する際のデータ移行は別途検証が必要。ブラウザ版の公開・配信はこの実装には含まない。


### 検証記録

- 保存専用のPlaywrightテストで、新規作成、街／探索の再読み込み、参照・乱数・ID、通常保存周期、各種選択待ち、死亡、帰還、複数タブ、保存失敗、破損復旧、デバッグ隔離、新規開始のキャンセル／確定、全消去、未対応版の保護、ブラウザ完全終了後の再開を検証する。
- 既存の追跡済み回帰スイート56本を実行。実行時エラーなし。8スイート内の12個のfalse値は変更前のHEADでも一致し、新規差分なし（状態そのものをfalseとして出力する検査も含む）。
- `feeltest.html` は変更前後とも38判定中29通過、同じ9項目が失敗。実行時エラーなし。過去の文書の「既知7件」とは数が異なるが、今回は実際の変更前HEADとの比較を基準にした。
- Chromium、390×844でタイトルと再開画面を目視確認。保存時間のサンプルは7階層で約0.2〜1.4ms、UTF-16換算の主データは約46〜255KB。これはPCでのスナップショット生成・書き込み計測であり、iPhone実機や最大戦闘負荷の性能保証ではない。
- 既存 `sweep.sh` はこのMacに `timeout` がないため動かなかった。同じ追跡済みテスト群をPythonのsubprocessの時間制限付きで実行した。未追跡の既存実験用スクリプトは本体回帰の対象に含めていない。
